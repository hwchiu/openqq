Developer architecture brief

Identity first.
Tenant policy second.

The Tenant Server is the policy boundary between Kubernetes ServiceAccount clients and the private OpenSandbox API. KFA verifies identity; PostgreSQL decides tenant authorization. They are separate responsibilities.

KFA TokenReview PostgreSQL mapping server key stays private
Important boundary

KFA never queries PostgreSQL and does not know tenant_id, scopes, quotas, or sandbox ownership. Tenant Server receives the verified identity, then performs the business authorization lookup.

One authenticated request, step by step

Example: GET /v1/sandboxes. Every protected request follows this boundary, even when KFA returns a cached identity.

Send request

Client sends its ServiceAccount token. The token is never logged or persisted by Tenant Server.

Build TokenReview

Tenant Server reads its own projected token and submits the client token as spec.token.

Verify identity

KFA authenticates Tenant Server, then verifies the client token and returns namespace, ServiceAccount, and cluster.

Map identity

Tenant Server queries PostgreSQL using cluster/namespace/serviceaccount.

Authorize

Check enabled state, required scope, request limits, quota, and sandbox ownership.

Proxy safely

Forward only allowlisted OpenSandbox routes with the private server credential.

Stream result

Copy command output or file bytes without buffering the complete response in memory.

Record usage

Record tenant-labelled status, duration, bytes, and ownership activity—not secrets or file contents.

Authentication cache semantics

Tenant Server calls KFA on every authenticated request. KFA's short cache determines whether full OIDC/JWKS verification repeats.

Cache missTokenReview reaches verification logic. KFA uses issuer metadata/JWKS, validates the token, and stores the result.
0–30 seconds · cache hitRepeated same-token requests still call the KFA HTTP endpoint, but KFA returns the cached identity without repeating full cryptographic verification.
After 30 secondsEntry expires or is evicted. The next request performs verification again. Rejected results use a 10-second negative TTL.
Authorization is not cached by KFA. Tenant Server still queries PostgreSQL for enabled mapping, scopes, quota, and ownership on every request. Disabling a tenant does not wait for KFA cache expiry.

Admin onboarding

Admin API uses KFA too, with a separate configured admin identity allowlist.

ADMIN_TOKEN=$(kubectl -n opensandbox-tenant-server create token \
  opensandbox-tenant-server --duration=10m)

curl -X POST http://<tenant-server-private-ip>:18080/admin/tenants \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "tenant_id": "team-a",
    "cluster_name": "local-cluster",
    "namespace": "team-a",
    "service_account": "runner",
    "scopes": ["sandbox:read", "sandbox:command"],
    "max_concurrent_sandboxes": 3
  }'

No tenant API key or JWT is generated. The client later uses its own ServiceAccount token; Tenant Server maps that identity to team-a.
