01 / Product purpose

A secure execution plane for multi-tenant agents.

OpenSandbox Tenant Server is the application boundary that turns sandbox execution into a governed product: tenant identity, session ownership, warm resources, controlled egress, streaming files, and evidence-based operations.

● Tenant-aware● Private OpenSandbox● FQDN egress● Warm pool● 5 min TTL

01.1 / Product charter

這不是 proxy；這是一個 execution product。

Tenant Server 把一個「可以執行任意程式的 sandbox」轉成可被管理、計量、撤銷與恢復的租戶服務。它的價值不在於多包一層 HTTP，而在於把身份、資源與 runtime policy 綁在同一個 session 上。

problem

沒有邊界的 runtime

直接讓多個 client 使用 OpenSandbox key，會失去 tenant ownership、quota、audit 與 egress 控制，也無法知道哪個租戶造成 runtime 壓力。

product outcome

有責任歸屬的 session

每個 request 都能回答：誰在使用、使用哪個 sandbox、允許哪些外部網路、何時到期、發生錯誤後如何回收。

non-goal

不取代 OpenSandbox

Tenant Server 不重新實作 sandbox runtime。它是 tenant-aware control boundary，將已驗證的請求交給私有 OpenSandbox。

主要角色與責任

Tenant developer使用 Kubernetes ServiceAccount token 建立 session、執行 command、傳輸檔案。
Platform operator管理 tenant、quota、allowlist、pool capacity、DB、Grafana。
Tenant Server執行 authentication、authorization、ownership、proxy、audit。
OpenSandbox執行 sandbox lifecycle 與 runtime control。

Architecture decisions

Shared statePostgreSQL，不使用 replica local file。
CredentialKFA 驗證 ServiceAccount；OpenSandbox key 只存在 server-side secret。
IdentityMetrics 在 Tenant Server boundary 加 tenant label。
Networkdefault-deny；FQDN grant 必須可撤銷、可過期。

03.2 / State model

One session, three linked state machines.

Session ownership、egress grants 與 sandbox availability 不應混在一個 boolean 裡。分開的 state 讓重試、TTL 與故障補償可以安全執行。

ownership

Sandbox ownership

creating → allocated → releasedallocated → expired → releasing

以 tenant_id + sandbox_id 驗證每一次操作；row lock / lease version 防止兩個 replica 同時 claim。

egress

Egress grant

requested → activeactive → revoked / expired

只有 active grant 會產生 policy effect；revoke 必須可重複執行，不能因 rule 已不存在而卡住。

runtime

Pool availability

available → claimedclaimed → quarantine → available

reset 失敗的 Pod 不能回到 available；補償 worker 必須先修復或刪除。

07.1 / Failure design

每個失敗都要有隔離、重試或明確交付。

系統不應用「刪掉所有 Pod」作為一般恢復手段。先保留 state、辨識責任與影響範圍，再執行最小補償。

02 / Architecture

The Tenant Server is the product boundary.

External clients never receive an OpenSandbox server key or Kubernetes credential. Every request enters Tenant Server, which authenticates the tenant, checks ownership and quota, then uses private control-plane APIs.

Review ruleOpenSandbox Server is never an external integration endpoint. Tenant Server is the only component allowed to combine tenant identity with sandbox operations.
02.1 / Components

Every component has one job.

The architecture is intentionally split between product policy, runtime control, state, and evidence.

deployed

Tenant Server

Go service. Authenticates tenants, checks scopes and ownership, enforces limits, streams requests, and exposes tenant metrics.

3 replicas · private host IP · NodePort 30081
private

OpenSandbox Server

Upstream runtime API. Owns sandbox lifecycle and execution resources. Its server credential stays behind Tenant Server.

ClusterIP only · internal credential
target

Egress policy controller

Applies default-deny and per-sandbox FQDN grants. It receives validated requests, never arbitrary NetworkPolicy from clients.

grant → apply → audit → revoke
shared state

PostgreSQL

Stores identity mappings, sandbox ownership, egress grants, quotas, and audit events for every replica.

read-write service · HA target ×3
target

Warm-pool manager

Maintains available sandboxes, claims one atomically, replenishes on empty, and quarantines failed resets.

min_available=10 · idle TTL=300s
observable

Prometheus + Grafana

Scrapes Tenant Server, OpenSandbox, Kubernetes, Cilium, and etcd signals into operational dashboards.

03 / Workflows

Product behavior is a set of controlled state transitions.

The diagrams below describe the behavior users depend on, not just the services deployed in Kubernetes.

session lifecycle
01

Authenticate

Call KFA TokenReview, then resolve enabled tenant from cluster/namespace/serviceaccount.

02

Authorize

Check scope, quota, request size.

03

Claim

Lease warm sandbox or create new.

04

Reset

Clear old state and apply baseline deny.

05

Deliver

Return session only after verification.

egress lifecycle

FQDN request and revoke

Tenant Server validates ownership, hostname, port, allowlist and TTL. It records a requested grant, applies policy, then changes it to active. DELETE and idle expiry perform the same idempotent revoke/reset operation.

requested → active → revoked / expired
failure path

Quarantine is a product state

If cleanup or egress reset fails, the session is not delivered and the sandbox is marked quarantine. A retry worker may repair it; operators can see the reason in audit and metrics.

allocated → quarantine → releasing → available
04 / How to use

Use one Tenant Server session for the whole task.

The client uses one ServiceAccount token and one sandbox ID. Tenant Server owns upstream credentials, ownership checks, stream limits, and cleanup.

client_session.py
import json
import urllib.request

TENANT_SERVER = 'https://tenant-server.example'
CLIENT_TOKEN = 'projected_serviceaccount_token'

def request(method, url, body=None):
    data = json.dumps(body).encode() if body else None
    req = urllib.request.Request(url, data=data, method=method,
        headers={'Content-Type': 'application/json',
                 'Authorization': 'Bearer ' + CLIENT_TOKEN})
    with urllib.request.urlopen(req, timeout=60) as res:
        return json.loads(res.read())

created = request('POST', TENANT_SERVER + '/v1/sandboxes', {
    'timeout': 300,
    'metadata': {'client_session': 'demo-001'},
})
sandbox_id = created['id']
# Reuse sandbox_id for command, upload, download, then DELETE.

07 / Operations

Deployment topology and operating model.

Scale out

Any Tenant Server replica can serve the next request. PostgreSQL transactions and leases provide consistency; sticky sessions are not required.

Recover

On reset failure, quarantine the sandbox. On DB failover, retry with backoff. Never delete the database to recover an API process.

Security posture

OpenSandbox remains private. Only Tenant Server has the upstream credential. Egress starts default-deny and grants are revocable.

02.3 / KFA authentication

Identity verification and tenant authorization are separate calls.

The Tenant Server calls KFA for every protected request. KFA verifies Kubernetes identity; PostgreSQL authorizes the verified identity. KFA never queries PostgreSQL and never decides tenant scope or ownership.

request

1. Tenant Server calls KFA

It sends the client token as spec.token and its own projected ServiceAccount token as the caller credential.

cache

2. KFA may return cache

Every request reaches KFA, but authenticated results are cached for 30 seconds; rejected results use a 10-second negative TTL.

authorization

3. Tenant Server queries DB

After KFA returns identity, PostgreSQL checks enabled mapping, scope, quota and sandbox ownership on every request.

Failure boundaryMissing/invalid token or KFA failure returns 401; a valid identity without tenant mapping or scope returns 403; no OpenSandbox side effect occurs before these checks complete.
